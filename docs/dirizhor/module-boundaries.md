# Границы модулей

Этот документ превращает черновую концепцию «Дирижёра» в первый набор
технических границ. Названия модулей рабочие и могут уточняться, но сами
границы ответственности считаются базовыми для следующего слоя ТЗ.

## 1. UI

Пользовательский интерфейс для телефона и компьютера.

Отвечает за:

- ввод задач пользователем;
- показ статуса задач;
- просмотр результатов;
- подтверждение чувствительных операций;
- работу с документами, проектами, темами и решениями;
- отображение истории и журналов в разрешенном пользователю объеме.

Не отвечает за:

- прямое обращение к AI-провайдерам;
- прямое чтение файлов корпоративной памяти;
- самостоятельное принятие решений о доступе к данным.

## 2. Director API

Центральный API системы и единственная точка управления рабочими процессами.

Отвечает за:

- прием запросов от UI и внешних клиентов;
- создание задач;
- выбор сценария обработки;
- проверку прав;
- обращение к реестру памяти;
- передачу ограниченного контекста в Agent Gateway;
- сохранение результатов;
- запись audit-событий;
- координацию очереди задач.

Не отвечает за:

- хранение бинарных файлов;
- прямую реализацию конкретных AI-провайдеров;
- обход правил доступа ради удобства агента.

## 3. Memory Registry

Индекс корпоративной памяти.

Отвечает за:

- хранение карточек объектов памяти;
- поиск по темам, проектам, ключевым словам и связям;
- предоставление агентам только реестра или выбранных карточек;
- хранение связей между объектами;
- выдачу идентификаторов документов, нужных для задачи.

Не отвечает за:

- хранение полного содержимого больших файлов;
- прямое взаимодействие с AI-провайдерами;
- решение о том, имеет ли пользователь право открыть объект.

## 4. Document Store

Хранилище файлов и версий документов.

Отвечает за:

- хранение оригинальных файлов;
- хранение версий;
- выдачу конкретной версии по разрешенному запросу Director API;
- фиксацию технических метаданных файла;
- поддержку резервного копирования.

Не отвечает за:

- выбор контекста для AI;
- анализ содержания документов;
- принятие решений о бизнес-смысле документа.

## 5. Agent Gateway

Изолированный слой интеграции с AI-моделями и агентами.
Внутреннее взаимодействие фиксирует
[Agent Gateway Protocol v1](agent-gateway-v1.md).

Отвечает за:

- единый интерфейс вызова AI-провайдеров;
- адаптеры ChatGPT, Codex и будущих агентов;
- одноразовое получение уже замороженного разрешенного контекста;
- нормализацию ответов агентов;
- идемпотентную доставку lifecycle events Director API.

Не отвечает за:

- самостоятельный доступ к корпоративной памяти;
- сохранение результатов напрямую в память;
- изменение архитектуры процесса без Director API.

## 6. Task Queue

Очередь фоновых и долгих задач.

Отвечает за:

- постановку задач в очередь;
- повторные попытки;
- статусы выполнения;
- ограничение параллельности;
- обработку длительных операций чтения, анализа, индексации и вызовов AI.

Не отвечает за:

- бизнес-логику выбора документов;
- принятие решений о правах доступа;
- хранение raw capability, prompt, context или result в durable queue payload.

## 7. Audit Log

Неизменяемый или трудноизменяемый журнал действий.

Отвечает за:

- запись действий пользователя;
- запись действий Director API;
- запись запусков AI-агентов;
- фиксацию доступа к объектам памяти;
- фиксацию изменений документов, версий и решений;
- поддержку расследования инцидентов и восстановления истории.

Не отвечает за:

- хранение основного содержимого документов;
- замену бизнес-сущностей системы.

## 8. Auth/RBAC

Модуль авторизации, аутентификации и прав доступа.

Отвечает за:

- идентификацию пользователей;
- роли и права;
- проверку доступа к проектам, темам, документам и операциям;
- правила передачи данных AI-агентам;
- поддержку операций, требующих подтверждения пользователя.

Не отвечает за:

- хранение бизнес-документов;
- выбор AI-модели;
- генерацию ответов.

## Базовый поток между модулями

```text
UI
-> Director API
-> Auth/RBAC
-> Memory Registry
-> Document Store
-> Agent Gateway
-> Director API
-> Audit Log
-> UI
```

Task Queue подключается для длительных операций. Audit Log получает события от
Director API и критичных внутренних модулей.
