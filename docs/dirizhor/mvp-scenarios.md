# MVP-сценарии

MVP должен доказать не наличие множества агентов, а правильность базового
контура: пользователь работает через Дирижёра, память хранится отдельно, AI
получает только выбранный контекст, результат журналируется и может быть
сохранен.

## Сценарий 1. Добавить документ в корпоративную память

Цель: создать объект памяти и первую версию документа.

Шаги:

1. Пользователь загружает файл или вводит текст.
2. UI отправляет запрос в Director API.
3. Director API проверяет права через Auth/RBAC.
4. Document Store сохраняет файл или текстовую версию.
5. Memory Registry создает `memory_object` и `document_version`.
6. Audit Log фиксирует создание объекта и версии.
7. UI показывает карточку объекта.

Критерий готовности:

- объект виден в реестре;
- версия имеет `storage_uri` и `content_hash`;
- создание отражено в `audit_event`.

Reference-статус: критерий подтверждён для multipart document upload на полной
SQL-схеме v1. Production object storage, session identity и orphan cleanup ещё
не реализованы.

## Сценарий 2. Найти контекст по задаче

Цель: подобрать релевантные объекты памяти без чтения всего архива.

Шаги:

1. Пользователь описывает задачу.
2. Director API создает `task`.
3. Memory Registry ищет карточки по проекту, теме, словам и связям.
4. Дирижёр возвращает пользователю или агенту список кандидатов.
5. Пользователь подтверждает выбранные документы, если требуется.

Критерий готовности:

- поиск работает по карточкам реестра;
- полный текст документов не передается агенту на этом этапе;
- выбранные объекты фиксируются для следующего шага.

## Сценарий 3. Передать выбранные документы AI-агенту

Цель: выполнить AI-задачу на ограниченном разрешенном контексте.

Шаги:

1. Director API получает список выбранных `memory_object`.
2. Auth/RBAC проверяет права пользователя и допустимость передачи AI.
3. Director фиксирует ordered `agent_run_context`, точные `document_version`,
   sensitivity snapshot и `context_set_hash`.
4. Auth/RBAC выдает одноразовую capability с action `context_bundle.read`.
5. Director передает Gateway только dispatch envelope и capability.
6. Gateway redeem-ит capability; Director читает в Document Store только
   зафиксированные версии и возвращает ordered context bundle.
7. После принятого события `started` Gateway вызывает выбранного агента.
8. Gateway идемпотентно возвращает один terminal event Director API.
9. Audit Log фиксирует dispatch, получение контекста и итог запуска.

Критерий готовности:

- агент не имеет прямого доступа к Document Store;
- контекст запуска можно восстановить по `agent_run_context`;
- capability нельзя использовать дважды или расширить другим документом;
- повтор `execute` или event не создает второй provider call либо side effects;
- запуск имеет согласованный статус и audit-события.

Reference-статус: сквозной тест начинает сценарий с публичного upload, фиксирует
созданную версию в `agent_run_context`, выполняет одноразовый redeem через
Reference Gateway и атомарно сохраняет terminal result и audit trail. Создание
task/run, context freeze и capability выполняются public Director API без
тестового SQL seed операционных сущностей. Отдельный E2E покрывает external
policy confirmation перед dispatch.

## Сценарий 4. Сохранить результат AI в память

Цель: результат AI не теряется и не смешивается с утвержденными решениями.

Шаги:

1. Agent Gateway возвращает результат.
2. Director API показывает результат пользователю.
3. Пользователь выбирает: сохранить как черновик, отправить на доработку или
   отклонить.
4. При сохранении создается `memory_object` типа `ai_result`.
5. Memory Registry связывает результат с исходными объектами через
   `relationship`.
6. Audit Log фиксирует сохранение.

Критерий готовности:

- результат AI имеет отдельный тип;
- результат связан с источниками;
- результат не становится утвержденным решением без действия пользователя.

Reference-статус: public API читает temporary result с проверкой RBAC и
целостности bytes. Save создаёт frozen `ai_result_save` confirmation; approval
атомарно создаёт объект, первую версию, связи, завершает task и пишет audit.

## Сценарий 5. Зафиксировать решение

Цель: отделить анализ AI от решения пользователя.

Шаги:

1. Пользователь открывает результат анализа или документ.
2. Пользователь формулирует решение.
3. Director API создает `decision` со статусом `draft` или `approved`.
4. Memory Registry связывает решение с источниками.
5. Audit Log фиксирует автора, время и статус решения.

Критерий готовности:

- решение имеет автора-человека;
- решение связано с источниками;
- изменение утвержденного решения требует новой версии или связи `supersedes`.

## Сценарий 6. Восстановить историю решения

Цель: понять, почему и на основании чего было принято решение.

Шаги:

1. Пользователь открывает карточку решения.
2. Director API получает связанные документы, AI-результаты и audit-события.
3. UI показывает цепочку: источники, агентские запуски, результат, решение,
   последующие изменения.

Критерий готовности:

- видна цепочка происхождения решения;
- можно увидеть версии документов, использованные в AI-запуске;
- можно отличить AI-выводы от решения пользователя.

## Что не входит в первый MVP

- полноценный «Совет директоров AI»;
- автоматическое принятие решений;
- сложная онтология знаний;
- SAML, multi-provider SSO и автоматическая синхронизация корпоративного каталога;
- тонкая матрица прав на уровне абзацев;
- одновременная поддержка большого числа AI-провайдеров;
- автоматическая миграция всей старой корпоративной памяти.
